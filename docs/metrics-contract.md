# Контракт `dashboard/metrics.json` (v1.1)

Спільна домовленість між скілами (`stage-1-supplax`, `automation-portfolio-sync`) і дашбордом (`giga-brdg/automation-system`). Будь-яка зміна формату робиться спершу тут, потім у скілах і парсері.

## Навіщо
Числа «до / ціль / факт» і спосіб перевірки зараз губляться: `dashboard/ROI.md` передає лише текст і перше слово Measured/Estimated. `metrics.json` передає їх структуровано, а людське пояснення лишається в `docs/roi_explained.md`.

## Версії
v1.1 лише додає поля: `value_items`, `OpenQuestion.value_item_id`, `baseline.not_applicable_why`, `at_scale`. Файл без них валідний як і в v1. `version` лишається `1`, бо дашборд відхиляє будь-яке інше число.

## Джерело правди
- Розрахунки автоматизатора в `docs/roi_explained.md`: розділ «## Цінність» (гроші за статтями) і «## Метрики».
- `dashboard/metrics.json` генерується з нього скілом. Руками файл не редагують.
- Якщо цифр немає, їх не вигадують. Скіл питає, а якщо відповіді немає, записує відкрите питання.

## Формат

```json
{
  "version": 1,
  "launched_at": "2026-07-22",
  "metrics": [ <Metric>, ... ],
  "value_items": [ <ValueItem>, ... ],
  "at_scale": <AtScale | null>,
  "open_questions": [ <OpenQuestion>, ... ]
}
```

`launched_at`: дата запуску в прод, `YYYY-MM-DD` або `null`, якщо ще не запущено.
`value_items`: необов'язкове (v1.1), див. ValueItem.

### Metric
| Поле | Обов'язкове | Значення |
|---|---|---|
| `id` | так | kebab-case, стабільний і ніколи не змінюється |
| `name` | так | людська назва українською |
| `type` | так | `time`, `revenue`, `cost`, `quality`, `conversion`, `other` (A/B/C/D Оксани: revenue=A, cost=B, time=C, quality=D) |
| `unit` | так | одиниця: «год/міс», «%», «лідів/тиждень», «$/міс» |
| `direction` | так | `down` (менше краще) або `up` |
| `primary` | так | `true` рівно в однієї метрики |
| `baseline` | так, можна `null` | `{value, period, source, kind}`; `kind`: `measured` або `estimate`. Якщо зміряти неможливо: `{"value": null, "not_applicable_why": "..."}` (v1.1) |
| `target` | так, можна `null` | `{value, why}`; `why` пояснює, звідки ціль (бриф, керівник, розрахунок) |
| `method` | так | як перевіряємо після запуску: що з чим порівнюємо, на якому періоді, хто міряє |
| `check_every_days` | так | як часто міряти, ціле число |
| `measurements` | так, може бути `[]` | лише дописується, див. нижче |
| `money` | ні | Має бути `null`, якщо є `value_items` (гроші рахуються в одному місці). Інакше `null` або `{rate_usd_per_unit, realization, realization_why}`. Для `time`: ставка $/год (8 спеціаліст, 15 менеджер) і коефіцієнт реалізації Оксани (0.9 не наймаємо, 1.0 скорочення, 0.5 переключення на продажі, 0.3 лише розвантаження) |

`period`: `YYYY-MM-DD..YYYY-MM-DD` або текст, якщо точного немає (тоді `kind` = `estimate`).

### Measurement
`{date, period, value, source, kind, note}`, де `date` — коли зміряно, `period` — за який період, `kind` — `measured` або `estimate`.

Правило append-only: записи з попередньої версії файлу не змінюються й не видаляються. Помилкову цифру виправляють новим записом з `note`: «виправлення заміру від DD.MM: причина».

### ValueItem (v1.1)
Стаття грошової цінності: що автоматизація дає на місяць і чому саме стільки. Генерується з таблиці «## Цінність» у `roi_explained.md`, `check_metrics.py` звіряє їх поле за полем.

| Поле | Значення |
|---|---|
| `id` | kebab-case, унікальний серед статей |
| `category` | `revenue` Дохід, `cost_savings` Економія витрат, `time` Час, `losses` Менше втрат (A/B/C/D Оксани), `run_cost` Експлуатація (витрати на саму автоматизацію) |
| `title` | що саме дає, людською мовою |
| `usd_per_month` | число; `run_cost` від'ємне або 0, решта більше 0 |
| `kind` | `estimate` або `measured`. `measured` лише при `basis: data` і точному періоді заміру `YYYY-MM-DD..YYYY-MM-DD` у `source` чи `formula`. «Підтверджено» в репо не пишуть: це ставить тільки дашборд після вердикту адміністратора |
| `basis` | `data` (обсяг з даних) або `assumption` (припущення) |
| `formula` | арифметика з одиницями: «1,2 фінала/міс × $290» |
| `why` | чому так, обмеження, що вже враховано, щоб не рахувати двічі |
| `source` | звідки цифри: скрипт, вигрузка, документ, людина |
| `as_of` | `YYYY-MM-DD` |
| `metric_ids` | необов'язкове: список id пов'язаних метрик або `null` |

`usd_per_month`, `formula`, `why`, `source` можуть бути `null` лише з OpenQuestion з `value_item_id` цієї статті й тим `field`.

### AtScale (v1.1)
Необов'язковий блок «повний масштаб» для автоматизацій, які зараз працюють на малому обсязі, але мають погоджений цільовий обсяг. Холодні імейли: зараз 4 ящики = $932/міс, на обсязі ТЗ (500–600 контактів/день) ≈ $5 000–6 000/міс. Без нього цінність такого проекту виглядає вп'ятеро меншою, ніж те, під що його будували, а з ним ніхто не плутає поточні гроші з майбутніми.

```json
"at_scale": {
  "usd_per_month_low": 4976,
  "usd_per_month_high": 5989,
  "volume": "500–600 контактів/день (11–13 тис./міс)",
  "condition": "11–13 тис. нових контактів/міс, 20–24 прогріті ящики, людина на відповіді",
  "formula": "та сама формула, що в статтях цінності, на обсязі ТЗ, мінус сервіси $264–299",
  "source": "ТЗ Максима 05.10.2026; CRM-когорта colddesigner",
  "as_of": "2026-10-28"
}
```

| Поле | Обов'язкове | Значення |
|---|---|---|
| `usd_per_month_low` | так | нижня межа, число більше 0. Чисте значення на місяць після експлуатації, не оборот |
| `usd_per_month_high` | ні | верхня межа, не менша за `low`. Може дорівнювати `low` або бути `null`: тоді це одна цифра, а не вилка |
| `volume` | так | обсяг, на якому порахували: «500–600 контактів/день (11–13 тис./міс)» |
| `condition` | так | що має бути правдою, щоб цей обсяг узагалі поїхав (люди, ящики, ліміти) |
| `formula` | так | арифметика з одиницями, та сама, що в статтях цінності, але на обсязі ТЗ |
| `source` | так | звідки обсяг і цифри: ТЗ, вигрузка, людина |
| `as_of` | так | `YYYY-MM-DD` |

Правила:
- `at_scale` дозволено лише коли є `value_items`: повний масштаб це та сама формула на іншому обсязі, без статей на поточному обсязі його нема з чого рахувати.
- Порожнім поле може бути лише з OpenQuestion, де `metric_id` і `value_item_id` обидва `null`, а `field` = `at_scale.<поле>` (питання про `at_scale` покриває всі поля блоку).
- `kind` не потрібен: обсягу ТЗ ще немає, тому зміряти його ніде, це завжди оцінка.
- `at_scale` **ніколи** не входить у суми: ні в `value_summary()`, ні в «Разом», ні в «## Actual Results» `ROI.md`. Поточні гроші й гроші на масштабі не додаються й не змішуються.
- У `dashboard/ROI.md` в `## Hypothesis` допустимий рядок «На повному масштабі: ~$X–Y/міс (оцінка)». Скіл його не вимагає і не перевіряє.

### OpenQuestion
`{metric_id, value_item_id, field, question, ask_whom, since}`
- `metric_id`: id метрики або `null`. Ключ обов'язковий (як у v1).
- `value_item_id` (v1.1, необов'язковий ключ): id статті цінності або `null`. Заповнене рівно одне з двох; обидва `null`, якщо питання загальне.
- `field`: назва поля, наприклад `baseline`, `target` чи `formula`.
- `ask_whom`: `automator`, `department_lead`, `crm_query`, `manual_measurement` або ім'я людини.
- `since`: дата, коли питання з'явилось.

## Обов'язкові значення і що робити, якщо їх немає
Скіл перевіряє кожну метрику. Для кожного поля, яке порожнє або `null`, але має бути заповнене, він **питає автоматизатора** через `AskUserQuestion` (до 4 питань за раз). Варіанти відповіді:
1. дати значення (і джерело);
2. «Не знаю, хто знає: ...» → створюється OpenQuestion з `ask_whom`;
3. «Неможливо зміряти, бо ...» → для `baseline`: `{"value": null, "not_applicable_why": "..."}` прямо в JSON. Для інших полів такого виходу немає, лише OpenQuestion.

Стара поблажка v1 («метрика згадана в Caveats» замість відповіді) у `check_metrics.py` лишилась попередженням, а не помилкою. Дашборд `roi_explained.md` не читає і такий файл відхиляє (так було з HRsupplax cc6a441), тому причину треба перенести в `not_applicable_why`.

Що вимагає відповіді:
- Метрика без `baseline` після запуску. До запуску baseline теж треба, бо Оксана: «без заміру до не стартуємо».
- Метрика без `target`.
- Метрика без `method` або `check_every_days`.
- `money` для `time` без `realization_why`.
- Стаття цінності без `formula`, `why`, `source` чи `usd_per_month`.
- Прострочений замір: `launched_at + check_every_days`, або останній замір + `check_every_days`, раніше за сьогодні. Скіл пропонує додати замір.

Скіл ніколи не підставляє правдоподібне число замість відповіді. Оцінку автоматизатора можна записати лише з `kind: "estimate"` і з джерелом («оцінка автоматизатора: 15 хв × 40 разів, слова керівника»).

## Що рахує дашборд (не скіл)
- Статус метрики:
  - «Немає даних»: немає baseline і замірів;
  - «Очікуємо»: є baseline, замірів після запуску ще немає;
  - «Виміряно»: є хоч один `measured` замір після `launched_at`;
  - «Підтверджено»: Оксана підтвердила в дашборді конкретний sha.
- Результат: останній замір проти baseline з урахуванням `direction`.
- Гроші: з `value_items`, якщо вони є (сума за категоріями, `run_cost` віднімається); інакше з `money`: різниця × ставка × realization. Оцінку й факт рахує окремо.
- Статус статті «Підтверджено» після вердикту адміністратора.

`dashboard/ROI.md` «## Actual Results» при наявних `value_items` починається з двох рядків, які рахує `check_metrics.value_summary()`: «Заміряно $X/міс, оцінка $Y/міс» і «За категоріями: ...». «Заміряно» це `kind: measured`, не вердикт.
- Множники стратегічності й тиражованості на сторінці цінності не використовуються.
